# docker-watcher Graphify Refresh — Design

Status: **Requirements, design, and tasks confirmed; `.superpowers/sdd/GATE_OPEN` recorded.** Local implementation and deterministic verification are complete. Production graph mutation remains gated by the live-acceptance safeguards in `tasks.md`.

## 1. Verified deployment contract and proposed invocation

Portainer inspection found the deployed `graphify-mcp` container running Graphify `0.9.67`, with `/srv/mcp-grafana/graphify-out` mounted at `/data` and `/scratch/workspace` mounted at `/workspace`. The default graph is `/data/graph.json` (39,246,926 bytes). `/workspace/docker-watcher` exists at commit `3506148fb54236c0e19551055d300a10cc34cae4`; the aggregate graph manifest contains `docker-watcher/...` paths, including `docker-watcher/app.py` in graph sources. `/workspace/docker-watcher/graphify-out/graph.json` is absent; the deployment has one aggregate workspace graph, not a per-repository graph.

The deployed MCP endpoint is authenticated and exposes read/query tools, not an index-refresh operation. Its server reloads a graph when the file's mtime or size changes on a later tool call. The installed CLI provides `graphify update <path>`; this synchronously re-extracts code files without an LLM round trip, not docs, papers, or images. `GRAPHIFY_OUT=/data` selects the shared graph output directory. The production update has not run; it remains gated by the live-acceptance safeguards in `tasks.md`.

The watcher cannot reach the Graphify HTTP service on its separate Docker network: `graphify-mcp` DNS resolution failed and a TCP probe to `172.28.0.5:8080` timed out. A read-only command was run inside the running `docker-watcher` container, via Portainer-assisted container exec: `docker exec -e GRAPHIFY_OUT=/data graphify-mcp graphify check-update /workspace/docker-watcher` exited 0 using the watcher’s configured `DOCKER_HOST`. This proves that the Docker CLI route can execute that check, but not the proposed standard-library HTTP client or full production update. The proposed route uses the existing socket-proxy: negotiate an Engine API version with `GET /version`, resolve the exact `graphify-mcp` name, then use `exec create`, `exec start`, and `exec inspect`. It does not call the Graphify MCP endpoint or expose its API key.

Run the fixed argv `["graphify", "update", "/workspace"]` with `GRAPHIFY_OUT=/data`, not an update rooted at an individual repo. Create the Docker exec with stdin/stdout/stderr unattached and `Tty=false`; start detached (`Detach=true`, `Tty=false`) and inspect its ID. The aggregate graph uses workspace-relative source paths and `/workspace` preserves those identities. The installed Graphify `0.9.67` CLI calls `_rebuild_code(..., block_on_lock=True)` and uses `out/.rebuild.lock`; with `GRAPHIFY_OUT=/data` this is `/data/.rebuild.lock`. The watcher still enforces one workspace exec at a time and never relies on concurrent waiters being serialized by Graphify’s lock. A Graphify CLI update is code-only.

Use Docker Engine ExecInspect’s nullable `ExitCode` without coercing JSON `null` to zero. Portainer observations on Docker Engine `29.8.1`: a newly created, unstarted no-op exec returned `Running=false, ExitCode=null`; the same exec after start returned `Running=false, ExitCode=0`; a running `sleep` exec returned `Running=true, ExitCode=null`; starting an already-run exec returned HTTP 409 `already run`. Recovery matrix: `Running=true` means retain/poll; non-null exit code means terminal (0 success, nonzero failure); `Running=false, ExitCode=null` means not started and the saved exec can be started; missing ID or container replacement is unresolved. Persist a `start_requested` state before POST start. After an ambiguous start response, inspect the saved ID; if still not started, retry that ID, and treat 409 as a signal to inspect rather than create a replacement. Never infer success from a missing/default exit code.

An exec ID is the Docker handle, not a Graphify job ID. Persist it with the Graphify container ID and the repo target generation before starting. A lost create response can leave only an unstarted orphan; back off and safely create a replacement. A Graphify container replacement that makes a saved ID uninspectable remains unresolved rather than proof of failure.

Graphify serves the updated aggregate graph on the next read after its file stat changes. The workspace is a separate checkout from docker-watcher’s temporary build clone; its checked-out revision may differ from the pushed revision when indexing runs. The user accepts this push-to-build race. Do not add snapshots, clone transfer, synchronization, or revision pinning.

## 2. Integration boundaries and state

Keep Docker build success observable separately from tag publication. Persist a per-repository target generation immediately after successful build completion and before refresh scheduling or tag pushes. A crash before this state commit can lose the trigger; no pre-build marker or build replay reconciliation is in scope. Graphify-only failures never use the `BuildError` path and cannot stop remaining tag pushes or repositories.

Keep per-repository target/completed generations, failure count, retry eligibility, and safe outcome. Add one workspace-wide active-exec record with the target-generation snapshot, attempt phase, start-requested marker, conservative crash-recovery fallback deadline, Docker exec ID, and Graphify container ID. A workspace exec scans the whole mounted source root and counts as in-flight for every repo; only one watcher-owned exec may be active or unresolved at a time. New repo builds during it advance their durable target and coalesce into one follow-on. An unresolved exec blocks all repos until safely resolved. Preserve prior state compatibility.

Persist every transition that enables an external action first. If persistence fails, suppress dependent create/start/inspect/follow-on actions. Before exec create, persist the attempt start and fallback deadline: attempt start plus the conservative delay for the next failure among the snapshot targets (60 seconds initially, then doubled up to 30 minutes). Persist the returned exec ID before start. A lost create response cannot have started the command; an orphan unstarted exec is safe to abandon. After start, reconcile only through the saved ID. If status cannot be safely resolved, retain the workspace-wide unresolved state rather than replaying or overlapping. Graphify’s shared `/data/.rebuild.lock` is additional defense, not the watcher’s serialization mechanism.

## 3. Lifecycle and scheduling

- **New successful build:** persist a new per-repository target generation. If that repo has no pending retry and there is no workspace exec/unresolved attempt, persist a snapshot of all outstanding targets and create the workspace exec immediately in that cycle. An active workspace job counts as in-flight for every repo because each invocation scans the shared source root. Refresh errors do not block image pushes or processing other repos.
- **Pending retry:** advance that repo target to its newest successful build without launching solely because of that build or changing its eligibility. If another eligible repo target triggers a workspace update, its snapshot may include this target; only verified terminal success can clear it.
- **Active workspace exec:** persist newer generations for any repo; do not create another exec. After terminal success, acknowledge only the persisted snapshot and clear retry state only for repos whose snapshot generation reached their latest target. If any newer target is eligible (no retry deadline or its due time has arrived), persist and run one coalesced follow-on. If all newer targets have future retry deadlines, retain them and their unchanged clocks until the earliest deadline.
- **Create:** persist attempt state and fallback deadline before Docker exec create. A definite create failure or timeout has no Graphify side effect because create cannot start the command; increment failure counts for the snapshot targets and schedule each retry from failure observation using 60-second/doubling/30-minute-cap backoff. A lost create response may leave an unstarted orphan; retain targets and use the fallback deadline before another create.
- **Start:** persist `start_requested` before calling exec start. On definite start rejection, inspect the same ID; if still unstarted, record the observed failure for snapshot targets and retry only when their persisted failure deadlines are due. On timeout/connection loss, retain the ID and inspect next cycle. If `Running=false, ExitCode=null`, retry start on that same ID only after any persisted failure deadline or crash-recovery fallback deadline. If `Running=true`, poll; if `ExitCode` is non-null, process terminal status. A 409 `already run` is reconciled by inspect, never by creating a second exec.
- **Running/poll error:** inspect at most once per normal watcher cycle. Poll errors retry next cycle without another exec. Keep a running or unresolvable exec indefinitely; no elapsed deadline authorizes replacement or replay.
- **Terminal exit 0:** persist success for the attempt snapshot before clearing it. Newer repo targets remain dirty; preserve their retry count and due time if the successful snapshot did not include that generation.
- **Terminal nonzero:** retain all targets dirty at failure observation, including targets accumulated after the attempt snapshot; one workspace exit code cannot identify per-file failures. For every dirty repo, increment its observed-failure count and schedule eligibility from this failure-observed time using that repo’s 60-second initial delay, doubling after each observed failure to a 30-minute cap. Coalescing alone never resets eligibility. Persist retry state and a distinct attempt-start fallback deadline before another create.
- **Restart recovery:** an attempt without an exec ID may create only after its persisted fallback deadline; an ID without `start_requested` may start only after that deadline; a `start_requested` ID is inspected first. Definite create/start/terminal failures use each repo’s durable known-failure deadline, which takes precedence over fallback. A definite start rejection with a future due time cannot start early. `Running=true` remains pending; a non-null exit code is terminal; `false/null` is not started and may be retried only after the applicable persisted deadline. If terminal transition persistence fails, retain the ID and inspect again; never create a replacement. An uninspectable ID/container replacement blocks all repos until the same ID resolves or an operator makes a separately approved recovery decision.

Each successful build has a durable per-repo target generation once its state commit completes; a crash before the commit can lose the trigger as documented. Retry timing/failure count remains per repo even though one workspace exec may satisfy multiple generations. A failed/skipped/unchanged build does not create a target. No refresh attempt begins before its enabling state write succeeds.

## 4. Logging and secret handling

Emit structured `graphify_refresh` events for detected failure conditions using fixed internal outcomes such as `exec_create_error`, `exec_start_unconfirmed`, `exec_running`, `exec_failed`, `exec_inspect_error`, `unresolved_exec`, and `persist_failure`.

- Repo identifiers come only from configured values after canonical bounded validation; otherwise use a fixed safe hash or `unknown`.
- Docker exec IDs are logged only after strict bounded opaque-token validation; otherwise omit or hash them. External status values map to a fixed enum.
- Never log Graphify stdout/stderr, credentials, raw Docker responses, request payloads, raw exception strings/tracebacks, raw hosts/paths, or unvalidated status values.
- Graphify-only events never start with the existing literal `build failed` prefix.
- Report retry delay/next eligibility only after its state transition is durably persisted; failed writes explicitly indicate `not_persisted`.

## 5. Configuration and deployment

Use the existing configured `DOCKER_HOST` and fixed Graphify container name, command, target, and output path. Use a standard-library transport supporting the current TCP endpoint and documented Unix-socket fallback; negotiate a Docker Engine API version via bounded `GET /version`. Use the Docker Engine exec lifecycle so the single workspace execution ID and container ID are inspectable; preserve nullable `ExitCode`. The watcher enforces one active exec globally; Graphify `0.9.67`’s `/data/.rebuild.lock` is additional defense only. Expose `GRAPHIFY_DOCKER_REQUEST_TIMEOUT_SECONDS` (default 10 seconds) to bound each create/start/inspect HTTP request; there is no overall process timeout. No Graphify API key, watcher-to-Graphify network change, extra workspace mount, or new Graphify endpoint is needed.

## 6. Compatibility, verification, and acceptance

Keep existing image build/push behavior and state readable. Extend deterministic `test_app.py` coverage for target persistence/order, push-failure retention, no trigger on skipped/unchanged/failed builds, first refresh failure not stopping pushes, global active workspace serialization, all-repo coalescing while active, unresolved attempt blocking across repos, retry/backoff/restart, nullable ExecInspect recovery matrix, create/start ambiguity, one inspect per cycle, terminal outcomes, persistence-failure suppression, and secret-free events. Test the case where repo B gains a generation after repo A’s snapshot and A’s workspace exec exits nonzero; B receives the same observed-failure accounting as other dirty targets. Test B-only not-due dirty state waits after success, and an eligible A follow-on can include and satisfy B’s not-yet-due target.

Before the first production update, establish an exclusive maintenance window: freeze the `/workspace` source tree, pause watcher refresh submissions, drain and inspect its active exec state, and prohibit all other Graphify writers through backup, update, validation, or restore. Check free space, then archive all `/data` graph/update files to a timestamped backup under `/data/.graphify-refresh-backups/` (excluding prior backups); verify archive readability and checksum. After the update, parse `graph.json` and `manifest.json`, compare unaffected-repo graph nodes/edges (or an explicitly justified stable identity equivalent) against the frozen pre-update baseline, and read the updated default graph through Graphify MCP. On any discrepancy, restore the archive, validate restored parsing/coverage/readback, then resume writers; if source freeze, exclusive coordination, or a durable backup is unavailable, do not mutate production.

Separately perform live acceptance through the deployed watcher and Portainer: verify the configured Docker Engine route, Graphify container identity, CLI exit/exec-inspect interpretation, update of shared `/data/graph.json`, and subsequent Graphify read reload. Local tests can be complete without live access; if the smoke cannot run safely, record the exact prerequisite and leave end-to-end acceptance open.
